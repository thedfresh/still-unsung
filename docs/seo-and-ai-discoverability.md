# SEO and AI discoverability

Research for the public pages of the new app. Search engines and AI systems must find the
archive, understand it, and cite it. This document gives a recommendation for each of eight
questions. It ends with the changes for the implementation tickets, the data-model decisions, and
suggested follow-up tickets.

- Research date: 2026-11-16. Facts about AI crawlers change fast. Re-check each source before launch.
- Scope: research only. No app code changes.
- Ticket: HSA-136. It feeds HSA-39 (SEO implementation), the public page tickets and HSA-28
  (data model).

## How to read this document

Each recommendation has a timing label:

- **Now**: decide or build it before the public pages are built. It is cheap now and costly later.
- **Launch**: build it before the new site goes live.
- **Deferred**: do not build it yet. The reason is stated.

A source note says how well a claim is backed: **primary** (the vendor's own page), **secondary**
(news or blog), or **our docs** (the Next.js docs in `node_modules/next/dist/docs/`, which match
the installed version 16.4.6).

## 1. Crawl access

### The crawlers (as of 2026-11-16)

Crawlers fall into three groups. The group decides what a `robots.txt` rule controls.

| Group | What it does | Crawlers |
|---|---|---|
| Training | Collects pages that may train models. | `GPTBot` (OpenAI), `ClaudeBot` (Anthropic), `Google-Extended` (a token, see below), `CCBot` (Common Crawl) |
| Search index | Builds the index that answer engines search. | `OAI-SearchBot` (OpenAI), `Claude-SearchBot` (Anthropic), `PerplexityBot`, `Googlebot` |
| User-triggered | Fetches one page because a person asked. | `ChatGPT-User` (OpenAI), `Claude-User` (Anthropic), `Perplexity-User` |

Facts and sources:

- **OpenAI** has `OAI-SearchBot` (search), `GPTBot` (training), `ChatGPT-User` (user actions) and
  `OAI-AdsBot` (ad page checks). Its page says robots.txt rules "may not apply" to `ChatGPT-User`,
  because a user starts the action. A site opted out of `OAI-SearchBot` is not shown in ChatGPT
  search answers. Changes take about 24 hours. (primary: developers.openai.com/api/docs/bots,
  read 2026-11-16)
- **Anthropic** has `ClaudeBot` (training), `Claude-SearchBot` (search quality) and `Claude-User`
  (user-triggered). All three honor robots.txt, including `Crawl-delay`. A rule that names
  `ClaudeBot` wins over the general setting. Anthropic began to read a machine-readable "no AI
  training" signal on 2026-10-30, based on an IETF AIPREF draft. It warns that IP blocking does
  not give a reliable opt-out. (primary: support.claude.com/en/articles/8896518, read 2026-11-16)
- **Google**: `Google-Extended` is a robots.txt token, not a separate crawler. It controls use
  of content that Google's normal crawlers already fetched, for Gemini training and for
  grounding. It does not affect Search ranking or inclusion. `Googlebot` feeds Search. Google's
  page does not say how AI Overviews relate to the tokens. Google says it plans to support
  AIPREF in early 2027. (primary: developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers, read 2026-11-16)
- **Perplexity** has `PerplexityBot` (search, "not used to crawl content for AI foundation
  models") and `Perplexity-User` (user-triggered, "generally ignores" robots.txt). It publishes
  IP lists. (primary: docs.perplexity.ai/docs/resources/perplexity-crawlers, read 2026-11-16)
- **Common Crawl** runs `CCBot`. Its open dataset is a common source of training text. Some
  bots falsely claim to be `CCBot`, so verify by reverse DNS under `crawl.commoncrawl.org` or by
  its published IP list. (primary: commoncrawl.org/ccbot, read 2026-11-16)
- `llms.txt` and the AIPREF signal are covered in questions 6 and 1 below.

### Recommendation

**Launch.** Allow all of them. The archive wants to be in the models, and the content is a
research archive with no paywall.

```txt
# robots.txt (generated by src/app/robots.ts)
User-agent: *
Allow: /
Disallow: /admin
Disallow: /api/
Sitemap: https://<canonical-host>/sitemap.xml
```

- Do not write per-vendor groups. One `*` group allows every named crawler too, and it removes
  the risk of a typo that blocks a crawler. Add a vendor group only to change one vendor's
  behavior. Remember that a named group replaces the `*` group for that bot, so repeat the
  `Disallow` lines inside it.
- Keep `/admin` and `/api/` disallowed. The admin is not public. The API rule keeps crawlers
  from fetching JSON that duplicates the pages. If a public data export is added later (question
  6), give it its own allowed path.
- A robots.txt `Disallow` does not hide a page. The admin needs real access control (HSA-135).
  Also send `X-Robots-Tag: noindex` from the admin routes. (**Launch**)
- **Do not block by IP or by user agent in the proxy** for AI vendors. Anthropic warns that it
  breaks opt-out signals, and the policy is "allow".
- **Rate limit, do not ban.** AI crawlers can send many requests. Set a proxy rate limit per IP
  that returns 429 with `Retry-After`. Cached pages are cheap, so the app should cope. (**Launch**)
- **Verify before trusting.** User-agent strings are easy to fake. When a log analysis needs
  certainty, match the published IP lists (OpenAI, Perplexity, Common Crawl) or reverse DNS.
- **Training preference signal (AIPREF): defer.** The standard is still a draft, and our policy is
  "allow". Revisit if the policy changes. (**Deferred**)
- **Decision for the user:** the "allow all" default is kept. Say so on the ticket if it changes.

## 2. Rendering

### Findings

- Server Components render on the server by default (`docs/CONVENTIONS.md`, section 2). A page
  that follows the conventions sends its content in the HTML. Client components are small leaves
  that need state.
- Google renders JavaScript in a second step, but its guidance says "not all bots can run
  JavaScript". Server-rendered HTML is the safe path. We do not know that AI crawlers render
  JavaScript, so we must not depend on it. (primary: Google JavaScript SEO basics, read
  2026-11-16)
- **Streaming risk.** With Cache Components, the server sends a prerendered shell, and parts
  inside `<Suspense>` stream in later. The streamed parts are still HTML in the same response.
  A crawler that reads the whole response sees them. A crawler that stops reading early, or a
  client that does not read the stream to the end, may not. (our docs: `02-guides/streaming.md`)
- **Status code risk.** After streaming starts, the server cannot change the status code. A
  `notFound()` inside a Suspense boundary returns 200 with a `noindex` meta tag. The same
  applies to `redirect()`: it becomes a client-side redirect, not an HTTP 301. This breaks the
  slug redirects of question 5. (our docs: `02-guides/streaming.md`)
- **Metadata risk.** Next.js waits for `generateMetadata` before it streams the page to bots
  it classifies as "HTML-limited". Other clients get metadata streamed with the content, which
  can land in `<body>`. (our docs: `streaming.md`, `htmlLimitedBots`)
- **Build risk.** The conventions say pages that show database content call `await connection()`
  before the cached read, so the cache fills at request time. An HTML-limited bot re-renders the
  page dynamically. Both paths must work at request time. (our docs: `streaming.md`)
- `partialPrefetching: true` is set in `next.config.ts`. It changes client navigation, not the
  HTML a crawler gets.

### Recommendation (**Now**, as page rules)

1. **Every fact on a public page is in the server HTML.** That means title, summary, set lists,
   dates, sources, citations and the `<script type="application/ld+json">` block.
2. **Resolve the entity before any Suspense boundary.** Look up the slug first, call `notFound()`
   for a missing entity, and issue the 301 for an old slug, all before the first `<Suspense>`
   and before any `loading.tsx` fallback renders. Then the status code is real.
3. **Keep the SEO-critical content out of Suspense.** Page title, summary, structured data and
   set list render in the main shell or in one cached read. Use Suspense only for secondary
   blocks (related shows, long lists).
4. **No content behind client-only code.** Do not load text or tables in `useEffect`, and do not
   hide text in tabs that render only after a click. Collapsed sections must still be in the HTML
   (use `<details>` or CSS, not conditional rendering).
5. **Test it.** Add an e2e test that loads each page type with JavaScript disabled and checks
   for the title, the summary, one performance row, the canonical link and the JSON-LD block. Add
   a second check that a missing slug returns HTTP 404 and an old slug returns HTTP 301. Run both
   with a plain `fetch` request as well as a browser. (**Launch**, built with the first public
   page)
6. **Do not add a user agent trick.** Serve the same HTML to everyone. Never serve crawlers
   different content (cloaking).

## 3. Structured data

### Rules

- Use JSON-LD, in a `<script type="application/ld+json">` tag in the page. Next.js recommends this
  and says to escape `<` as `<`. Use one helper that does it
  (`src/lib/json-ld.ts`, built with its first user). (our docs: `02-guides/json-ld.md`;
  primary: Google structured data guidelines)
- Google says: "Don't mark up content that is not visible to readers of the page." Markup must
  match the visible page. (primary: developers.google.com/search/docs/appearance/structured-data/sd-policies,
  read 2026-11-16)
- Give every entity a stable `@id` (its canonical URL plus a fragment, for example
  `https://<host>/songs/ripple#song`). Link entities with `@id` references instead of copying
  them.
- Validate with the schema.org validator in CI or by hand. The `schema-dts` package gives types
  at no runtime cost. (**Launch**)

### Type mapping

| Our entity | schema.org type | Notes |
|---|---|---|
| Event (show) | `MusicEvent` | `startDate`, `location` (a `MusicVenue` or `Place`), `performer` (a `MusicGroup` or `Person`), `subEvent`, `recordedIn`. `MusicEvent` adds no properties of its own; it inherits from `Event`. |
| Set | `MusicEvent` as a `subEvent` of the show, or a plain `ItemList` | Prefer `ItemList` of performances. A set has no date or place of its own. |
| Performance | `ListItem` in the set's `ItemList`, with `item` pointing to the song | A performance is "one song in a set". schema.org has no type for it. Do not invent one. |
| Song | `MusicComposition` | `name`, `lyricist`, `composer`, `sameAs`. `recordedAs` links the studio recordings that we know. |
| Musician | `Person` (or `MusicGroup` for a band) | `sameAs` to Wikidata and MusicBrainz. |
| Venue | `MusicVenue` or `Place` | `address`, `geo` if known, `sameAs`. |
| Recording | `MusicRecording` with `recordingOf` the song | Use `recordedAt` and `datePublished` only when known. Link to the event with `recordedIn` on the event. |
| Archive / data export | `Dataset` + `DataDownload` | Only when an export exists. See question 6. |
| Site | `WebSite` and `Organization` on the home page | Name, URL, logo, `sameAs`. Optional `SearchAction`: skip it. |
| Breadcrumb | `BreadcrumbList` | One per page below the home page. |

Which of these produce Google rich results is not the goal. Google's rich-result support for music
types is small. The goal is a clear, machine-readable statement of what each page is about. Models
and knowledge-graph builders read it, and it costs little. (opinion; source for the Google limits:
Google's structured data gallery, to re-check at launch)

### Uncertain and partial data without false claims

Our data has three-state flags (`true`, `false`, `null` for "not known") and partial dates
(`year`, `month`, `day` stored separately; `docs/CONVENTIONS.md` section 4).

| Case | Rule |
|---|---|
| A flag is `null` | **Omit the property.** Never output `false` for "not known". Never output `true` for "probably". JSON-LD has no "unknown" value, and absence is the honest form. |
| A flag is `true` or `false` | Output it only if the page also shows it, and only if a schema.org property fits. |
| Full date | `startDate: "1980-06-14"` (ISO 8601). |
| Year and month only | `startDate: "1980-06"`. schema.org `Date` accepts ISO 8601 partial dates. |
| Year only | `startDate: "1980"`. |
| Date unknown | Omit `startDate`. Show "date unknown" in the visible text. |
| Date is a best guess (`dateUncertain` is true or null) | Do not put a precise date in `startDate`. Use the coarser value we are sure of, or omit it. Put the uncertainty in visible text ("probably 1980"). Do **not** use `eventStatus` for it: that property is for cancelled or postponed events. |
| Order of performances in a set is uncertain | Still use `ItemList` positions, but show the uncertainty in the visible text. Do not claim a precise order in `position` when the data says it is a guess. |
| Source disagreement | Say so in the visible page and give the sources. Structured data carries the one value we publish as ours. |
| `privateNotes` and other curator-only fields | Never in JSON-LD, never in HTML. |

- **Add a test.** A unit test over the JSON-LD builders checks that a `null` flag produces no
  property and that a partial date produces a partial ISO date. (**Launch**)
- **Decision needed (HSA-28):** how the model records "date is a guess" separately from "date is
  partial". Today `dateUncertain` is a flag. The page and the markup need a clear rule for how it
  displays. See the data-model list below.

## 4. Entity identity

Goal: a model or a knowledge graph can tell that our "Robert Hunter" page is the same person as
the Wikidata and MusicBrainz records, and that our "Ripple" page is the same song.

### Recommendation

- **Store external identifiers on the entity (Now, data model).** Per musician: Wikidata QID,
  MusicBrainz artist MBID, Wikipedia page title, and optionally VIAF, Discogs and Library of
  Congress IDs. Per song: Wikidata QID, MusicBrainz work MBID, and ISWC if known. Per venue:
  Wikidata QID and MusicBrainz place MBID. Per recording: MusicBrainz recording or release MBID.
  Store them as plain nullable text columns, or as one `external_id` table keyed by entity and
  `source`. The second form scales better (HSA-28 decides).
- **Output them as `sameAs` (Launch).** `sameAs` takes the full URLs, for example
  `https://www.wikidata.org/entity/Q…` and `https://musicbrainz.org/artist/<mbid>`. Only list a
  link a person has checked. A wrong `sameAs` merges two entities in a graph, which is a false
  claim at scale.
- **Our own stable IDs.** Keep the canonical URL as the stable ID (question 5). Do not use the
  database integer ID in public URLs. Use it nowhere in markup.
- **Matching process (Launch).** An admin step or script proposes a Wikidata or MusicBrainz match
  for each musician and song. A person confirms each match. Do not auto-accept fuzzy matches.
  The match tool is a follow-up ticket.
- **Wikidata item for the site itself: defer.** Wikidata accepts an item that is a clearly
  identifiable entity described by "serious and publicly available references", or one that
  fills a structural need. (primary: wikidata.org/wiki/Wikidata:Notability, read 2026-11-16)
  A new site has no independent coverage yet, so the item might be deleted. Revisit after the
  site gets press, citations in books or papers, or a Wikipedia mention. (**Deferred**)
- **Link from Wikipedia: ask later, do not ask now.** Wikipedia editors remove self-promotion.
  An external link from Wikipedia is accepted when the page is a reliable source with
  content the article cannot hold, for example a performance database. Do not add the link
  ourselves, because that is a conflict of interest. The right path is: build the archive, get
  cited by others, then propose the link on the article's talk page and let an independent editor
  decide. (**Deferred**; this is general Wikipedia policy and should be re-checked on the
  "Conflict of interest" and "External links" policy pages before any proposal)
- **Add the data to external graphs instead.** The archive could contribute facts to MusicBrainz
  and Wikidata (for example performance dates with sources). That increases our presence in the
  graph, and it follows each project's rules. (**Deferred**; follow-up idea, not a ticket yet)

I could not confirm the Wikidata QID or MusicBrainz MBID for Robert Hunter from search results.
A person must look them up and confirm that they match the right Robert Hunter. Several people
share the name.

## 5. Canonical signals

### Recommendation

- **One URL per entity (Now).** Each event, song, musician, venue and recording has exactly one
  canonical path built from its stored slug. Never serve the same entity at a second path.
  Lists, filters and search results are different pages with their own rules.
- **Descriptive slugs stay.** The data-model session decided this. Numeric IDs would be a
  downgrade. The fix for change is redirects.
- **301 for old slugs (Now design, Launch build).** A changed slug keeps a redirect from the old
  one (`docs/CONVENTIONS.md` section 1). The lookup runs before any Suspense (question 2) and
  returns HTTP 301 to the canonical path. Never chain redirects. If an entity is merged into
  another, the old URL redirects to the surviving entity. If an entity is removed, return 410 or
  404, not a redirect to the home page.
- **Canonical link on every page (Launch).** Set `alternates.canonical` in metadata to the
  absolute URL. Use one configured site origin (an environment value, for example `SITE_URL`),
  never the request host. Redirect `www`, `http` and uppercase variants to the one canonical form
  at the proxy.
- **Trailing slash and case.** Pick one form (no trailing slash, lower case) and redirect the
  other. The Next.js default removes the trailing slash.
- **Query strings.** Pages that take sort, filter or paging parameters set a canonical link to
  the clean URL, or to the page with the paging parameter only. Do not index filter combinations.
  Mark empty or thin result pages `noindex`. (**Launch**)
- **Same text, one place.** Do not copy a song summary onto each performance page. Link to the
  song page.
- **"How to cite this page" block (Launch).** Each entity page shows:
  - the permanent URL (the canonical one, as plain text and as a link);
  - a suggested citation in one line: *Author or site name, "Page title", Site name, URL,
    accessed date*;
  - the date of the last content change, taken from `updatedAt` (`docs/CONVENTIONS.md` section 3
    requires this column on every editable table);
  - the license (question 6).

  Machines read the same fields from `dateModified`, `url` and `license` in the JSON-LD.
- **Permanent URL.** "Permanent" means we promise that the path keeps working through redirects.
  Say so on a short "Citing the archive" page that the block links to. Do not claim a DOI or any
  identifier that does not exist.
- **Sitemap lists only canonical URLs** (question 6).
- **Open Graph and Twitter cards (Launch).** Next.js generates them from `generateMetadata` and
  the `opengraph-image` file convention. They matter for social links, and some AI answer tools
  show the preview image. (our docs: `01-getting-started/14-metadata-and-og-images.md`)

## 6. Machine-readable access

| Item | Verdict | Timing | Reason |
|---|---|---|---|
| `sitemap.xml` | Build | **Launch** | Cheap. Crawlers use it to find every page. It also carries `lastModified`. |
| Open data license | Choose and show | **Now** (decision), **Launch** (show) | Without a license, reuse and citation are unclear. |
| `robots.txt` | Build | **Launch** | Question 1. |
| Public JSON API | Reuse the planned `/api/v1/` | **After launch** | The conventions already plan `/api/v1/` for "a future public API, LLM tools". Build read-only list and detail routes when a user need appears. |
| Bulk data export (CSV or JSON dump) | Defer | **Deferred**, but design for it | A dump lets researchers and model builders get the data without scraping. It needs a license, provenance filtering and a privacy review (no `privateNotes`). |
| `Dataset` markup | With the export | **Deferred** | It describes a download that does not exist yet. |
| `llms.txt` | Skip for now | **Deferred** | See below. |
| MCP server, semantic search, chat | Parked | **Deferred** | The LLM features ticket is parked. See "Design with awareness". |

### Sitemap

- Use `src/app/sitemap.ts`. For more than 50,000 URLs, use `generateSitemaps` to split the file.
  The Next.js docs say Google's limit is 50,000 URLs per sitemap. (our docs:
  `03-api-reference/03-file-conventions/01-metadata/sitemap.md`)
- The sitemap reads from the data layer, with a cache tag, and calls `await connection()` so the
  build does not read the database (`docs/CONVENTIONS.md` section 5). A write that adds or removes
  a public entity refreshes the sitemap tag.
- Include only canonical, indexable, public URLs. Set `lastModified` from `updatedAt`. Leave out
  `priority` and `changefreq`, which Google ignores. (secondary: common SEO guidance; re-check)
- Submit the sitemap in Google Search Console and Bing Webmaster Tools. This also gives crawl
  reports. (**Launch**)

### `llms.txt`: defer

- `llms.txt` is a proposed file that lists a site's key pages for language models.
- Google's John Mueller said on 2025-06-17 that no AI system uses it, and compared it to the old
  keywords meta tag. Later reports say Google still does not use it, and that few AI requests
  reach these files. (secondary: Search Engine Roundtable, Search Engine Land, Ahrefs study,
  read 2026-11-16. I did not find a primary statement from an AI vendor that it reads the file.)
- The cost is small, but the evidence of benefit is weak. The sitemap, clean HTML and JSON-LD
  already do the same job for the crawlers that exist.
- Revisit when an AI vendor documents that it reads `llms.txt`, or when the MCP or API work
  starts. At that time, a short `llms.txt` that points to the API and to the license is cheap.
  (**Deferred**)

### License

- The archive combines facts (dates, set lists), our own editing and research text, and some
  third-party material (images, quoted text, recordings). One license does not fit all.
- **Recommendation, to confirm with the user (Now):** publish the factual data (events, sets,
  performances, dates) under an open data license, and keep text and images under a separate
  statement. Candidates: CC0 or ODbL for the data, CC BY or CC BY-SA for our text. Facts are
  weakly protected in many countries, but the database right applies in the EU. A clear license
  states our wishes. This is not legal advice.
- **Attribution is what gets us cited.** CC BY (or a data license with attribution, such as
  ODbL) asks reusers to credit the archive. CC0 asks nothing. If credit matters most, choose an
  attribution license.
- Do not license material we do not own. Images and third-party text need their own credit and
  permission lines (see the data-model item on image provenance).
- Show the license in the page footer and in the "Cite this page" block. Put the license URL in
  JSON-LD as `license`.

### Design with awareness (LLM features stay parked)

Costs nothing now, and avoids rework later:

- Keep research text as clean text tied to its source and citation (already the plan).
- Give every page a short, plain-text summary field. It is the same text used on the page
  (question 7) and later usable as a retrieval chunk.
- Keep `/api/v1/` detail responses stable and self-describing: canonical URL, `updatedAt`,
  source list, license. A future MCP tool wraps them.
- Mark each fact with its source, so a future chat feature can quote it with credit.
- Do not add vector search, embeddings or an LLM call now.

## 7. Content that models cite

Models quote pages that state facts plainly, near the top, with a source. They credit pages that
say who published the fact.

### Recommendation (**Launch**, as page content rules)

1. **Short factual summary at the top of each page.** One to three plain sentences that stand on
   their own, for example "Robert Hunter performed 'Ripple' N times between 1980 and 1990 in
   this archive." The text comes from data, not from an LLM, so it is correct by construction.
   Build it with a function per entity type, and unit test it, including the uncertain and
   partial cases ("an unknown date", "about 1980").
   - Say "in this archive" or "in the archive's records". It makes a true, bounded claim, and
     it names us.
2. **Name the entity in full in the first sentence.** "Robert Hunter (lyricist, 1941–2019)", not
   "he". Models often lift a single paragraph.
3. **Visible dates, in full.** Show the event date in words and in a `<time datetime="…">`
   element. Use the same partial-date text as the JSON-LD. Show "Last updated" and the
   citation block (question 5).
4. **Visible sources.** Each fact that came from a source shows it: a recording, a ticket, a
   book, a contributor. Link to the source when it is public. A page with "Sources" is easier to
   trust than a bare list. Use `cite` and a short list, not a long bibliography.
5. **State uncertainty in words.** "The date is uncertain" is more useful, and more honest, than
   silence. It also stops a model from presenting a guess as a fact.
6. **Descriptive titles and headings.** Title format: `Ripple – songs – <Archive name>`. One
   `<h1>` per page. Use headings in a logical order. Tables use `<th>` and a caption.
7. **Descriptive link text and internal links.** Link song to the events where it was played and
   back. Use the song's name as link text. Every public page must be reachable by links from the
   home page, not only from the sitemap and search.
8. **Plain HTML tables for set lists.** Do not use images of text. Alt text on all images.
9. **No hidden text for machines.** Hidden text violates search guidelines.
10. **Stable, quotable identifiers.** Show the show date in `YYYY-MM-DD` form somewhere on the
    page for each event, because people and models quote it.
11. **Keep the name of the project consistent.** Use one name for the site everywhere (title,
    footer, JSON-LD `name`, citation). A model credits what it can name.
12. **Accessibility helps here.** Landmarks, headings and text alternatives serve screen readers
    and crawlers. The e2e axe tests already guard this.

## 8. Measurement

### Recommendation

1. **Server logs by user agent (Launch).** The proxy (nginx) writes an access log with the
   user agent and the status code. A small script groups requests by crawler name (`GPTBot`,
   `OAI-SearchBot`, `ChatGPT-User`, `ClaudeBot`, `Claude-SearchBot`, `Claude-User`,
   `PerplexityBot`, `Perplexity-User`, `CCBot`, `Googlebot`, `bingbot`, `Google-Extended` is not a
   user agent and never appears). Report requests per week, the share of 200, 301, 404 and 429,
   and the most requested paths.
   - Verify the large or suspicious sources by IP list or reverse DNS, as the vendors publish.
   - Logs hold IP addresses. Keep them short-term (for example 30 days) and keep the report
     free of personal data. This repository is public: commit scripts, never logs.
2. **Referrer data (Launch).** Answer engines often send a visitor when a user clicks a citation.
   Count visits whose referrer is `chatgpt.com`, `perplexity.ai`, `claude.ai`, `gemini.google.com`
   and similar, and any `utm_source` they add. Names of domains change, so keep the list in one
   file and review it. Use privacy-friendly analytics that does not need a cookie banner. The
   choice of tool is a decision for HSA-39 or a follow-up.

## Items that need a data-model decision (HSA-28)

1. **External IDs.** Where do Wikidata, MusicBrainz and other IDs live: columns on each entity, or
   one `external_id` table keyed by entity type, entity ID and source? The table is more
   flexible. It needs a rule for IDs that have been checked by a person.
2. **Slug history.** A table of old slugs per entity (already planned). Questions: one table or
   one per entity, how a merge keeps all old slugs, and how a delete (410) differs from a
   redirect.
3. **Canonical slug rules for events.** An event slug derives from the date and timing. When a
   date changes from partial to full, the slug may change. The redirect table must handle it
   every time. Decide whether the slug may contain a placeholder for an unknown part.
4. **"Date is a guess" versus "date is partial".** `year`, `month`, `day` give partial. What
   states "we believe 1980 but we are not sure"? The page, the summary text and the JSON-LD need
   one rule (question 3). Decide the field and its allowed values.
5. **Per-fact sources.** Which facts carry a source: date, venue, set order, musician? The
   "visible sources" rule (question 7) needs a link from each such fact to a source record. This
   links to the provenance work and to the research-text design for later LLM use.
6. **Summary text.** Do we generate the summary from data (recommended), or store an editable
   summary per entity? If stored, add a column. If generated, no change. Either way, decide that
   the text is never produced by an LLM without review.
7. **Last-modified date.** `updatedAt` exists on every editable row. A page changes when a child
   row changes (a performance edit changes the show page). Decide whether the page's
   `dateModified` is the maximum over the children, or a stored value touched on each write.
8. **Public or not.** Which rows are public? Tags for visibility must be in the data model so that
   the sitemap and JSON-LD never expose private rows. `privateNotes` never leaves the data layer.
9. **License per record.** If the site mixes licenses (own text, third-party images), decide
   whether a record carries a license or credit field. Image provenance is already in the
   data-model scope.
10. **Venue identity over time.** A venue keeps one slug across name changes (already planned).
    JSON-LD should carry the name at the time of the show if it differs. Decide the field for that.
